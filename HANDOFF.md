# TTR LP02 Dashboard - Handoff

Formula Student dashboard. STM32H743 on a 极客 core board, 480x272 RGB panel via
LTDC, listens on CAN, drawn with LVGL 9.4.

Work in progress lives on **`refactor/vehicle-data-and-ui-binding`**, branched
from `main`. `main` still holds the original firmware and is a working fallback.

---

## Environment

| | |
|---|---|
| Toolchain | arm-none-eabi-gcc, found automatically under `C:\ST\STM32CubeIDE_*` |
| Build | CMake + Ninja |
| Host compiler | any MinGW-w64 (TDM-GCC works), only for the simulator |
| Python | 3 with Pillow, only for the asset tools |
| Programmer | STM32CubeProgrammer |

```powershell
git clone --recurse-submodules <url>      # LVGL is a submodule pinned to v9.4.0
```

Forgetting `--recurse-submodules` leaves `Drivers/lvgl` empty and CMake fails
with no LVGL sources.

## Build

**Firmware**

```powershell
cmake --preset debug
cmake --build --preset debug
```

Output `build/debug/DashBoard_re_1010.elf`. Flash with the `STM32: flash debug`
VS Code task, or open the project in STM32CubeIDE - both build systems coexist
and produce identical binaries.

**Simulator** (runs the real UI code in a desktop window)

```powershell
cmake -S sim -B sim/build -G "Ninja"
cmake --build sim/build
sim\build\dashboard_sim.exe                       # windowed
sim\build\dashboard_shot.exe out.bmp 6000         # headless screenshot at t=6000ms
```

**QSPI external loader**

```powershell
cd tools\qspi_loader
cmake -S . -B build -G "Ninja" -DCMAKE_TOOLCHAIN_FILE=../../cmake/arm-none-eabi-gcc.cmake
cmake --build build
```

## Architecture

```
CAN ISR -> can_rx -> can_decode -> vehicle_data -> ui_bind -> EEZ screens
```

Each layer knows only its neighbours. The point of the split is that
**redesigning the UI only touches `ui_bind.c`**; before the refactor a single
`updatescreen()` hard-coded several hundred widget names and any layout change
broke the build.

| File | Role |
|---|---|
| `Core/User/can_rx.c` | Ring buffer. The ISR only enqueues. |
| `Core/User/can_decode.c` | Unpacks frames into `vehicle_data`, from the main loop. |
| `Core/User/vehicle_data.h` | The data model. **The only interface between CAN and display.** |
| `Core/User/ui_bind.c` | Implements the `get_var_*()` functions EEZ declares. The only file allowed to know widget names. |
| `Core/User/nav.c` | Page order, button debounce, the both-held gesture. Shared with the simulator. |
| `Core/User/bsp_*.c` | SDRAM, MPU/cache, display, QSPI. |
| `Core/User/ui/` | Generated by EEZ Studio. **Never hand-edit.** |
| `Core/User/ttr_can/` | Generated from the DBC. **Never hand-edit.** |

Directory convention matches `TTR_LP02_VCU`: `Core/Inc` and `Core/Src` hold only
CubeMX output; everything hand-written lives in `Core/User` with headers beside
sources.

## Things that will cost you a day if you don't know them

**FMC and QUADSPI are not in the `.ioc`.** They are hand-written in
`bsp_sdram.c` and `bsp_qspi.c` because the project's HAL version matches no
local CubeH7 package. CubeMX does not know those pins are taken and will hand
them to other peripherals on regeneration. **Read the pin tables at the top of
`bsp_sdram.h` and `bsp_qspi.h` before opening the `.ioc`.**

**`MPU_Config()` from CubeMX is wrong** and marks 0x60000000-0xDFFFFFFF
no-access, which contains the SDRAM at 0xC0000000. `BSP_MPU_ConfigAndEnableCache()`
overrides it entirely from a USER CODE block. That single line is why the board's
32 MB of SDRAM works at all.

**Framebuffers must stay write-through in the MPU.** LTDC reads SDRAM directly
and never sees the D-cache; write-back would show tearing and stale pixels.

**`-u _printf_float` is required at link time.** newlib-nano omits floating
point printf, and without it every voltage renders blank.

**EEZ regenerates `Core/User/ui` wholesale but never deletes stale files.**
After changing the layout, check for orphaned `ui_image_*.c` - 29 of them once
sat there consuming 10% of flash for artwork nothing referenced.

**Fonts are the flash budget.** They reached 3.24 MB at one point. Keep large
display fonts at **bpp 4** and restrict the character range - the speed readout
only needs `45-57` (digits plus `- . /`). A font whose bitmap data exceeds 1 MB
also overflows LVGL's 20-bit `bitmap_index` and fails to compile.

**lv_conf.h only enables RGB565 in the software renderer.** Every other
`LV_DRAW_SW_SUPPORT_*` is 0 to save flash. Anything handing LVGL an image in
another format gets **nothing drawn and no error** - the pixels decode fine, the
widget is laid out, visible and the right size, and the screen stays black. The
GIF widget defaults to ARGB8888 and hit exactly this, which is why
`gif_pages.c` calls `lv_gif_set_color_format(gif, LV_COLOR_FORMAT_RGB565)`
before setting the source. If new artwork ever renders as nothing, check the
colour format before anything else.

**Don't apply a shared EEZ style to a bar.** The SOC bar's indicator silently
refused to paint while the custom `bar` style was applied; setting colours
directly on the widget fixed it. Root cause never found. If a widget mysteriously
does not render, try removing its custom style first.

**Verify UI changes in the simulator, not on the car.** It runs the same
`screens.c`, `ui_bind.c` and `gif_pages.c`. `dashboard_shot.exe out.bmp 13350`
renders the moment when SOC is 33%, which is a useful reference frame.

It also has the buttons - arrow keys, wired to the same `Nav_Scan()` at the same
5 ms period, so debounce and the one-second both-held gesture are the real ones
rather than an imitation. Adding a page or changing the order is a `nav.c` edit
that both builds pick up.

The simulator reads the QSPI image too. Point `TTR_QSPI_IMAGE` at a `qspi.bin`
and pass a page index as the third argument - 5, 6 and 7 are the debug pages:

```powershell
$env:TTR_QSPI_IMAGE = "qspi.bin"
sim\build\dashboard_shot.exe debug1.bmp 6000 5
```

`gif_pages.c` reaches the flash through `BSP_QSPI_GetMappedBase()` rather than
casting `QSPI_BASE_ADDR`, which is the seam that lets `sim/sim_qspi.c` answer
with a file instead of the register-level driver.

## Assets

**Fonts and layout** are edited in EEZ Studio, project at
`dashboard_layout/dashboard_layout.eez-project`. Output path is already set to
`..\Core\User\ui`. Project type must be **LVGL** (not Dashboard), resolution
480x272.

Variables bound to a label's text **must be typed `string`** - EEZ's native mode
does no number-to-text conversion, and a `float` bound to a label produces code
that will not compile.

**Animations** are too large for internal flash and live on the QSPI part:

```powershell
python tools\gif_optimize.py dashboard_layout\gif -o dashboard_layout\gif\optimized
python tools\make_qspi_image.py dashboard_layout\gif\optimized -o qspi.bin
STM32_Programmer_CLI -c port=SWD mode=UR -el W25Q64_TTR.stldr -w qspi.bin 0x90000000
```

12.2 MB of sources compress to 3.64 MB at 200 px and 17 fps. The firmware boots
normally when the QSPI is blank - it checks for a magic word rather than handing
0xFF to the decoder.

## Hardware facts, all confirmed on the board

| | |
|---|---|
| SDRAM | W9825G6KH, 32 MB at 0xC0000000, SDCLK 120 MHz, CAS 3 |
| QSPI flash | W25Q64, JEDEC `0xEF4017`, 8 MB at 0x90000000 |
| Panel | 480x272, LTDC pixel clock 11.54 MHz, **73.2 Hz refresh** |
| Buttons | PB14, PB15. Both held 1 s toggles the FPS overlay. |
| CAN | FDCAN2, PB12/PB13, interrupt priority 0 |

Carrier board schematic checked: nothing it drives overlaps the FMC or QUADSPI
pins.

## Current state

Working and verified on hardware: display, CAN decode, speed/LV/HV/SOC, stale
detection (`---` when a signal times out), drive mode, startup sweep, splash
animation, SOC bar.

Flash 21.75% of 2 MB, RAM_D1 1.4% of 512 KB. Frame rate is capped by the panel
at 73 Hz; `LV_DEF_REFR_PERIOD` is 16 ms so the practical figure is ~62 fps.

### Open items

1. **QSPI write path is untested.** Flash the firmware, set
   `g_qspi_run_write_test = 1` in a debugger watch window, then read
   `g_qspi_write_test_result` - 1 pass, 0 fail, -1 not yet run. It erases and
   reprograms the last sector. **Do this before trusting the loader**, which
   shares the same code through `bsp_qspi.c`.
2. **The external loader has never run.** Builds clean with all six entry points
   and a valid `.Dev_Info`, but has not been used against CubeProgrammer.
3. **Animations render in the simulator but are unconfirmed on the board.** All
   three decode, animate and land in the right containers when the image is fed
   through `sim_qspi.c`. What that does not cover is reading them back out of
   the real flash part.
4. **Speed clips at the left edge** with three wide digits (`250` is cut, `147`
   is not). The label is content-sized and left-anchored; centring it in EEZ
   would fix it.
5. **`CAN_RX_IsLinkStale()` is not surfaced.** Per-signal staleness works;
   whole-bus loss has no dedicated indicator.
6. **An unused `lv` float variable** sits in the EEZ project bound to nothing.
7. **`.git` is about 630 MB**, mostly historical artwork and the previously
   vendored LVGL. Clone times suffer; not urgent.
